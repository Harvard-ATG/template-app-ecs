# Terraform Infrastructure

This directory contains Terraform configuration for deploying template-app-ecs to AWS ECS, following the [atg-ops-appserver](https://github.com/Harvard-ATG/atg-ops-appserver) pattern.

## Architecture

The application uses:
- **ECS Fargate** for containerized services (API)
- **ALB** from shared infrastructure (`atg-dev-default` cluster) for load balancing
- **RDS PostgreSQL** - Dedicated instance per environment (created by this Terraform)
- **ElastiCache Redis** - Optional dedicated instance per environment (created by this Terraform)
- **ECR** for Docker image storage
- **CodeBuild** for CI/CD (dev only)
- **SSM Parameter Store** for secrets (passwords auto-generated by Terraform)
- **Route53** for DNS
- **Splunk** for centralized logging

### Database Architecture

**Sessions are stored in PostgreSQL, not Redis**, making ElastiCache optional. This design:
- ✅ Simplifies infrastructure and reduces costs
- ✅ Maintains security and functionality
- ✅ Allows easy Redis addition later for caching or high-traffic scenarios

Each environment gets its own RDS instance:
- **Dev**: `db.t3.micro`, 7-day backups, single-AZ
- **Prod**: `db.t3.small`, 30-day backups, Multi-AZ for high availability

### Docker Image Build Strategy

**Dev Environment:**
- **Automated via CodeBuild** - Pushes to `main` branch trigger automatic builds
- CodeBuild pulls code from GitHub, builds Docker image, and pushes to ECR
- No manual docker commands needed after initial setup
- **No Docker Hub credentials required** - uses unauthenticated pulls (100/6 hours limit)

**Prod Environment:**
- **Manual build required** - You build locally and push to ECR
- Prevents accidental deployments from code commits
- Gives full control over production releases

**Local Development:**
- `docker-compose up` still works for local testing
- Local Docker Compose is separate from AWS/ECR deployment

### CodeBuild Configuration

The project includes a custom `buildspec.yml` that:
- ✅ Removes Docker Hub dependency (no credentials needed)
- ✅ Clones repository using SSH deploy key from SSM
- ✅ Builds using `packages/api/Dockerfile`
- ✅ Tags images with: `latest`, commit hash, date, branch name
- ✅ Pushes all tags to ECR
- ✅ Includes build metadata labels (OCI standard)

**Custom CodeBuild Module:**
- Located in `terraform/modules/codebuild/`
- Uses `buildspec.yml` from repository root
- Creates GitHub webhook for automatic builds
- IAM permissions for ECR push and SSM parameter access

## First-Time Setup

### 1. Provision SSM Parameters (Session Secret and Anthropic Key Only)

**Note**: Database passwords are now auto-generated by Terraform and stored in SSM automatically. You only need to provide:

```bash
# Session secret (generate random string)
aws ssm put-parameter \
  --name "/dev/template-app-ecs/session_secret" \
  --value "$(openssl rand -base64 32)" \
  --type SecureString

# Anthropic API key (optional, for LLM features)
aws ssm put-parameter \
  --name "/dev/template-app-ecs/anthropic_api_key" \
  --value "<your-api-key>" \
  --type SecureString

# Repeat for prod
aws ssm put-parameter \
  --name "/prod/template-app-ecs/session_secret" \
  --value "$(openssl rand -base64 32)" \
  --type SecureString

aws ssm put-parameter \
  --name "/prod/template-app-ecs/anthropic_api_key" \
  --value "<your-api-key>" \
  --type SecureString
```

### 2. Generate GitHub Deploy Key (Dev Only)

CodeBuild uses an SSH deploy key to clone the repository. This is the **only extra setup** needed for automated builds.

```bash
# Generate key pair
ssh-keygen -t ed25519 -C "codebuild-template-app-ecs-dev" -f template-app-deploy-key -N ""

# Add public key as deploy key on GitHub
# Go to: https://github.com/YOUR-ORG/template-app-ecs/settings/keys/new
# Title: "CodeBuild Deploy Key"
# Key: <paste contents of template-app-deploy-key.pub>
# ✓ Check "Allow read-only access"
# Click "Add key"

# Store private key in SSM
aws ssm put-parameter \
  --name "/dev/template-app-ecs/build_ssh_key" \
  --value "$(cat template-app-deploy-key)" \
  --type SecureString

# Delete local keys (security best practice)
rm template-app-deploy-key template-app-deploy-key.pub
```

**Note:** Docker Hub credentials are NOT required. The custom `buildspec.yml` uses unauthenticated pulls from Docker Hub, which provides 100 pulls per 6 hours (sufficient for most projects).

### 3. Initialize and Deploy

```bash
cd terraform/environments/dev
terraform init
terraform plan  # Review what will be created
terraform apply
```

**What gets created:**
- RDS PostgreSQL instance (`atg-template-app-ecs-dev`)
- ElastiCache Redis cluster (`atg-template-app-ecs-dev`) - optional, see "Disabling Redis" section
- ECR repository
- ECS service and task definitions
- Security groups
- Route53 DNS record
- CodeBuild project (dev only)
- IAM roles
- SSM parameter for database password (auto-generated)

**First deployment takes ~10-15 minutes** for RDS instance creation.

### 4. Build and Push Initial Docker Image

After `terraform apply` completes, the ECS service will try to pull the Docker image from ECR. You need to push an initial image:

#### Dev Environment (Automated via CodeBuild)

**Setup (One-Time):**
1. Ensure GitHub deploy key is configured (see step 2 above)
2. Terraform created CodeBuild project with webhook
3. Webhook triggers on pushes to `main` branch

**First Image Push:**
```bash
# Option A: Push to GitHub main branch (triggers CodeBuild automatically)
git push origin main

# Option B: Trigger CodeBuild manually via AWS Console
# Go to: CodeBuild → template-app-ecs → Start build

# Option C: Build and push locally (if CodeBuild not working yet)
cd /Users/vesnatan/Harvard/template-app-ecs
aws ecr get-login-password --region us-east-1 | \
  docker login --username AWS --password-stdin $(terraform -chdir=terraform/environments/dev output -raw ecr_repository_url)

docker build -t template-app-ecs:latest -f packages/api/Dockerfile .
docker tag template-app-ecs:latest $(terraform -chdir=terraform/environments/dev output -raw ecr_repository_url):latest
docker push $(terraform -chdir=terraform/environments/dev output -raw ecr_repository_url):latest
```

**Monitor CodeBuild:**
```bash
# Check build status
aws codebuild list-builds-for-project --project-name template-app-ecs

# View logs in AWS Console
# https://console.aws.amazon.com/codesuite/codebuild/projects/template-app-ecs
```

#### Prod Environment (Manual Build Required)

**Prod requires manual build and push** to prevent accidental deployments:

```bash
# 1. Login to prod AWS account
aws-login-saml --account tlt-prod

# 2. Build Docker image locally
cd /Users/vesnatan/Harvard/template-app-ecs
docker build -t template-app-ecs:v1.0.0 -f packages/api/Dockerfile .

# 3. Get ECR repository URL
cd terraform/environments/prod
ECR_URL=$(terraform output -raw ecr_repository_url)

# 4. Login to ECR
aws ecr get-login-password --region us-east-1 | \
  docker login --username AWS --password-stdin $ECR_URL

# 5. Tag and push to ECR
docker tag template-app-ecs:v1.0.0 $ECR_URL:v1.0.0
docker tag template-app-ecs:v1.0.0 $ECR_URL:latest
docker push $ECR_URL:v1.0.0
docker push $ECR_URL:latest

# 6. Update ECS service to pull new image
terraform apply -var="image_tag=v1.0.0"
```

### 5. Deploy Image to ECS

After the image is in ECR, update the ECS service:

```bash
# Dev - Force new deployment to pull latest image
aws ecs update-service \
  --cluster atg-dev-default \
  --service atg-template-app-ecs-api-dev \
  --force-new-deployment

# Or use Terraform (if task definition changed)
cd terraform/environments/dev
terraform apply

# Prod - Specify image tag
cd terraform/environments/prod
terraform apply -var="image_tag=v1.0.0"
```

**Monitor Deployment:**
```bash
# Watch service events
aws ecs describe-services \
  --cluster atg-dev-default \
  --services atg-template-app-ecs-api-dev \
  --query 'services[0].events[:5]'

# Check task status
aws ecs list-tasks \
  --cluster atg-dev-default \
  --service-name atg-template-app-ecs-api-dev

# Or use ECS Console
# https://console.aws.amazon.com/ecs/home?region=us-east-1#/clusters/atg-dev-default/services
```

### 6. Run Database Migrations

After the ECS service is running successfully:

```bash
# Dev
cd terraform
./run_migration.py dev

# Prod
./run_migration.py prod
```

The script will:
- Find the running ECS service and get its network configuration
- Run the migration task using the same VPC/subnets/security groups
- Output Splunk query and ECS console links for monitoring

**Verify migrations:**
```bash
# Check migration logs in Splunk
# index=soc-isites source=atg-template-app-ecs-dev "alembic"

# Or check ECS task logs
aws ecs describe-tasks \
  --cluster atg-dev-default \
  --tasks <task-arn-from-script-output>
```

Test the application:

## Ongoing Deployment Workflow

After initial setup, use these workflows for regular deployments:

### Dev Environment (Automated)

1. **Make code changes** and commit locally
2. **Push to main branch**: `git push origin main`
3. **CodeBuild automatically:**
   - Clones repository using SSH deploy key
   - Builds Docker image using `packages/api/Dockerfile`
   - Tags image as `:latest`
   - Pushes to ECR
4. **Deploy to ECS:**
   ```bash
   # Force ECS to pull latest image
   aws ecs update-service \
     --cluster atg-dev-default \
     --service atg-template-app-ecs-api-dev \
     --force-new-deployment
   ```
5. **Run migrations** (if schema changed): `./run_migration.py dev`

**CodeBuild Webhook:**
- Configured automatically by Terraform
- Triggers on pushes to `main` branch
- View builds: https://console.aws.amazon.com/codesuite/codebuild/projects/template-app-ecs

### Prod Environment (Manual)

1. **Tag a release** in the repo (e.g., `v1.0.0`)
2. **Build and push** to ECR:
   ```bash
   # Login to prod account
   aws-login-saml --account tlt-prod
   
   # Build Docker image
   cd /path/to/template-app-ecs
   docker build -t template-app-ecs:v1.0.0 -f packages/api/Dockerfile .
   
   # Get ECR repo URL from Terraform output
   ECR_URL=$(cd terraform/environments/prod && terraform output -raw ecr_repository_url)
   
   # Login to ECR
   aws ecr get-login-password --region us-east-1 | \
     docker login --username AWS --password-stdin $ECR_URL
   
   # Tag and push to ECR
   docker tag template-app-ecs:v1.0.0 $ECR_URL:v1.0.0
   docker tag template-app-ecs:v1.0.0 $ECR_URL:latest
   docker push $ECR_URL:v1.0.0
   docker push $ECR_URL:latest
   ```
3. **Deploy** with Terraform:
   ```bash
   cd terraform/environments/prod
   terraform apply -var="image_tag=v1.0.0"
   ```
4. **Run migrations** (if schema changed): `./run_migration.py prod`

### Understanding the Build Flow

**Three Separate Docker Contexts:**

1. **Local Development** (Docker Compose)
   - Command: `docker-compose up --build`
   - Uses: `docker-compose.yml` in project root
   - Purpose: Local testing with hot reload
   - Does NOT push to ECR

2. **Dev Deployment** (CodeBuild → ECR → ECS)
   - Trigger: Push to GitHub `main` branch
   - Builder: AWS CodeBuild
   - Uses: `packages/api/Dockerfile`
   - Destination: ECR with `:latest` tag
   - ECS pulls from: ECR

3. **Prod Deployment** (Manual → ECR → ECS)
   - Trigger: Manual docker build command
   - Builder: Your local machine
   - Uses: `packages/api/Dockerfile`
   - Destination: ECR with version tag (`:v1.0.0`)
   - ECS pulls from: ECR

**Key Differences:**

| Aspect | Local (Docker Compose) | Dev (CodeBuild) | Prod (Manual) |
|--------|------------------------|-----------------|---------------|
| **Build Location** | Local machine | AWS CodeBuild | Local machine |
| **Dockerfile** | Via docker-compose.yml | packages/api/Dockerfile | packages/api/Dockerfile |
| **Image Storage** | Local Docker cache | ECR | ECR |
| **Trigger** | `docker-compose up` | Git push to main | Manual command |
| **Purpose** | Development/testing | Dev deployment | Prod deployment |
| **Runtime** | Local Docker | ECS Fargate | ECS Fargate |

## Upgrading RDS Instance Size

RDS instance types can be changed **without data loss or recreation**. AWS applies the change during the maintenance window with minimal downtime (~5 minutes).

### To Upgrade

1. **Edit `terraform/environments/dev/variables.tf`** (or create `terraform.tfvars`):
   ```hcl
   rds_instance_class = "db.t3.small"  # Was db.t3.micro
   ```

2. **Apply changes:**
   ```bash
   cd terraform/environments/dev
   terraform plan  # Review the change
   terraform apply
   ```

3. **Terraform will show:**
   ```
   # module.rds.aws_db_instance.main will be updated in-place
   ~ resource "aws_db_instance" "main" {
       ~ instance_class = "db.t3.micro" -> "db.t3.small"
       ...
   }
   ```

4. **AWS applies the change:**
   - Queued during next maintenance window (default: Monday 4-5am UTC)
   - Or immediately if `apply_immediately = true` (causes ~5 min downtime)
   - Database remains available except during brief restart

### Available Instance Classes

| Class | vCPU | RAM | Use Case | Monthly Cost (us-east-1) |
|-------|------|-----|----------|--------------------------|
| `db.t3.micro` | 2 | 1 GB | Dev, low traffic | ~$14 |
| `db.t3.small` | 2 | 2 GB | Small prod apps | ~$29 |
| `db.t3.medium` | 2 | 4 GB | Medium traffic | ~$58 |
| `db.t3.large` | 2 | 8 GB | High traffic | ~$116 |
| `db.r6g.large` | 2 | 16 GB | Memory-intensive | ~$159 |

Multi-AZ (prod) doubles the cost but provides high availability.

### Storage Upgrades

Storage can be **increased but never decreased**:

```hcl
rds_allocated_storage = 50  # Was 20 GB
```

Storage autoscaling is enabled (up to 100 GB by default via `max_allocated_storage`).

## Disabling Redis (ElastiCache)

Redis is **optional** since sessions are stored in PostgreSQL. To disable ElastiCache and save ~$11-12/month:

1. **Comment out the ElastiCache module** in `terraform/environments/dev/main.tf`:
   ```hcl
   # module "elasticache" {
   #   source = "../../modules/elasticache"
   #   ...
   # }
   ```

2. **Update the app module call** to not use Redis:
   ```hcl
   module "template_app" {
     ...
     # redis_endpoint = module.elasticache.endpoint  # Comment this line
     redis_endpoint = ""  # Add this line
   }
   ```

3. **Apply changes:**
   ```bash
   terraform apply
   ```

The application will continue working with database-backed sessions.

## OIDC / Harvard Key Integration (Future)

The current ALB and DNS setup **fully supports OIDC** authentication for future Harvard Key integration. The architecture uses path-based routing which enables flexible authentication flows.

### Current Routing

```
https://template-app-ecs.dev.example.com/api/*  → Backend API
```

### With OIDC (Future Implementation Options)

**Option A: ALB-Level OIDC** (Recommended for simplicity)
```
ALB authenticates with Harvard Key
  ↓
ALB adds X-Amzn-Oidc-* headers
  ↓
Backend reads headers (no OAuth flow needed)
```

Benefits:
- No backend OAuth implementation needed
- ALB handles token exchange
- Backend just reads user info from headers
- Minimal code changes

**Option B: Application-Level OIDC** (More control)
```
https://template-app-ecs.dev.example.com/auth/login     → Backend OAuth initiation
https://template-app-ecs.dev.example.com/auth/callback  → Backend OAuth callback
https://template-app-ecs.dev.example.com/api/*          → Backend API (authenticated)
```

Benefits:
- Full control over authentication flow
- Can customize token handling
- Better for complex auth requirements

### Implementation Notes

1. **ALB listener rules** support OIDC authentication natively
2. **Path-based routing priorities** allow auth routes to take precedence
3. **No infrastructure changes** needed - just add OIDC configuration to existing ALB listener
4. **Frontend can be added** as a separate ECS service with priority routing:
   ```
   /auth/*     (priority 50)  → Backend OIDC handlers
   /api/*      (priority 100) → Backend API
   /*          (priority 200) → Frontend (Next.js)
   ```

See [AWS ALB OIDC docs](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/listener-authenticate-users.html) for implementation details.

## Troubleshooting

**Task fails to start:**
- Check task definition has correct environment variables
- Verify SSM parameters exist (`session_secret`, `anthropic_api_key`)
- Database password is auto-generated - check `/dev/template-app-ecs/database_password` exists in SSM
- Check security groups allow traffic from ALB to ECS
- Verify RDS security group allows traffic from ECS security group

**Health checks failing:**
- Verify health check path `/api/v1/health` returns 200
- Check container logs in Splunk
- Ensure database connection is working (check RDS endpoint in environment variables)
- Verify RDS instance is available (check AWS Console)

**Database connection errors:**
- Check RDS instance is running and available
- Verify security group rules allow ECS → RDS on port 5432
- Check database endpoint environment variable is correct
- Verify database password in SSM matches RDS master password
- Check VPN CIDR blocks are configured if connecting from local

**CodeBuild failing:**
- Verify build SSH key is correct in SSM: `/dev/template-app-ecs/build_ssh_key`
- Check deploy key is added to GitHub repo (Settings → Deploy keys)
- Ensure deploy key has "Allow read-only access" checked
- Review CodeBuild logs: https://console.aws.amazon.com/codesuite/codebuild/projects/atg-template-app-ecs-dev-image-build
- Check buildspec.yml exists in repository root
- Verify GitHub webhook is configured (auto-created by Terraform)

**Docker Hub rate limit errors:**
- Error: "Too Many Requests" or "429" when pulling images
- Solution: This is rare (<100 pulls/6 hours needed to hit limit)
- If needed, add Docker Hub credentials to buildspec.yml (see commented section)

**RDS instance creation slow:**
- Initial RDS creation takes 10-15 minutes
- Multi-AZ deployments (prod) take longer
- Check RDS events in AWS Console for progress

**ElastiCache errors (if enabled):**
- Verify ElastiCache security group allows ECS traffic on port 6379
- Check ElastiCache cluster is available
- Sessions work without Redis - consider disabling if not needed

## Naming Conventions

Following atg-ops-appserver patterns:
- Resources: `atg-{app_name}-{env}-{resource}`
- SSM params: `/{env}/{app_name}/{param_name}`
- Services: `atg-{app_name}-api-{env}`
- ECR repos: `{app_name}`
